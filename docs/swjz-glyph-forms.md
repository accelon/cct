# swjz 字頭的字形來源盤點（2026-11-06）

> 你問「swjz 字頭的字形有很多，找一下」。答案：**同一個字頭有 9 種形體承載管道**，
> 而且其中 3 種是**資料缺陷**（不是設計）。全部數字来自可重跑掃描，不靠肉眼。
>
> ```powershell
> bun run src/extract-adb.ts D:\accelon3\swjz.adb out/swjz   # 先解檔
> bun run src/glyph-audit.ts     # 純 code point 統計（輸出 ASCII，終端不會騙人）
> bun run src/glyph-forms.ts     # 九類管道分組統計
> bun run src/glyph-samples.ts   # 可疑字頭的原始行證據
> ```
> 結果檔：`out/glyph-audit.txt`、`out/swjz-glyphs.txt`、`out/glyph-samples.txt`、
> `out/swjz-glyphs.tsv`（10,706 條逐字頭）。

## 1. 九種字形承載管道（數量皆為实測）

| # | 管道 | 位置 | 實測 |
|---|---|---|---|
| ① | **正篆字頭**（真 Unicode 字） | `<字 id img>頭</字>` | 10,706 條 |
| ② | **重文**（同一部內依附本字的其他形體） | id 末位＝重文序 | **1,280**（末位 1→1,088、2→164、3→22、4→4、5→2）；末位 0（本條）9,426 |
| ③ | **體類標記**（古文／籒文／篆文／奇字／今文） | 字條第一條 `<粗>` 起首 | 古文 444、籒文 212、篆文 38、奇字 3、今文 1 ＝ **698** 條可擷取「本字」 |
| ④ | **行內篆體** | `<seal_script>字</seal_script>`（說解中引用的古文字形） | 標籤 **185** 次、落在 **117** 個字條 |
| ⑤ | **篆圖圖號** | `img="NNNa-NN"`／`NNNb-NN` | 10,706 條全有（a 冊 5,364／b 冊 5,336／`nil` **6**） |
| ⑥ | **構形說形** | 正文「从某、某聲」 | 9,868 條含「从」；536 條含 IDS 構形符 |

| ⑧ | **缺字佔位** | `？`(U+FF1F)／PUA／`□` | `？` **4,445** 次、PUA **173**、`□` 10、`●` 0；含佔位符的字條 **2,120** 條 |

（如「吹」×2：`w0220500`／`w3200050`，「右」×2、「否」×2、「廿」×2…）。

## 2. 字頭本體的码点分層（这才是「字形很多」的主因）

```text
CJK基本   7,749  (72.4%)     ← 任何字型都畫得出
Ext-B     1,948  (18.2%)  ┐
Ext-A       987  ( 9.2%)  ├ 2,937 條（27.4%）需要 Ext 字型，否則顯示 □／豆腐
Ext-C         2            ┘
Compat(U+F900)  1
Compat(U+2F800) 3   ← 兼容表意字（例 w0760161 U+2F802、w4050021 U+2F8D5）
IDS 當字頭      3   ← 例「⿰金⿱丣刀」「⿲矢𦣝亏」「⿰歹𦟀」
U+FFFD          1   ← 解碼失敗残留（w4230012，見 §3）
```

對互鏈的直接影响：**引用端若要拿字頭當 key，27.4% 必須能處理星體码點**；
這也解釋上一輪 `mengzi` 那類差異的成因型態——两端計數方式只要把代理對拆開就會偏。

## 3. 三類真正的資料缺陷（要回報，不自行替換）

1. **12 條字頭是圖號而不是字**：
   ```xml
   <字 id="w1320011" img="164a-06">（图164A-01）</字>   <!-- 全形括號＋页码 -->
   <字 id="w1460021" img="200b-04">（图200B-01）</字>
   <!-- 另有 w2060562 w2064121 w2340011 w3630012 等，共 12 條 -->
   ```
   → 這些字條**沒有可顯示、可搜尋的字頭**，`char:` 落地後標題欄會是「（图164A-01）」。
      形體只在外部書影圖上，而 `resources` 容器只有 `accelon3_logo.png`（`<圖>` 標籤出現 **0** 次）。
2. **1 條 U+FFFD**：`<字 id="w4230012" img="575a-03">？</字>`（码点 U+FFFD）
   → 來源轉碼時已丢字，不是字型問題，必須回原檔修。
3. **6 條 `img="nil"`**（有字頭但明確宣告無圖）：
   `w0540010 十`、`w0970031 𤕤`、`w1800580 餽`、`w4081320 𢠽`、`w4081330 慢`、`w5180011 𢀒`
   → 目前 `nil` 與 `有圖號` 混在同一欄位語意裡；UI 要能区分「無圖」跟「圖檔缺」兩回事。

另外 **2,120 條字條正文含 `？`／PUA 缺字佔位**（PUA 173 次、`？` 4,445 次）。
依 00-common §6「發現缺字／誤字只回報，不自行替換」，我不做任何替換。

## 4. ③ 的重文↔本字鏈能不能用

698 條可擷取本字的重文裡：

- **518 條**本字確實另立字條（例：`弌←古文一`、`丄←篆文上`、`𢂇←古文帝`、`𣃟←古文㫄`、
  `𥘅←古文示`、`𠃞←古文禮`）→ 可以直接生成「重文→正篆」的庫內連結。
- **180 條**本字在書中查無字條（例 `雱←籒文。`，擷取到的「本字」是句讀符）
  → 其中一部分是我的擷取規則太窄（`籒文。`、`或从某`、`篆文从某` 等變體），
    一部分是真缺陷。要把這 180 條再拆一輪才能定案。

## 5. 對互鏈／UI 的三條具體影響（接 `docs/link-efficiency-2026-11-06.md`）

1. **字頭搜索必須走码点**：2,937 條星體字頭，若 UI 端用 UTF-16 長度或 BMP-only 正則，
   會出現「查得到字條但標題错位」；母區 `han.ts` 已規定 `\p{Script=Han}` ＋代理對＝1，
   兩端要同一套（這次我自己就先踩過，見 §6）。
2. **12 條圖號字頭建議在 UI 標「形體僅見書影」**，並讓 `char:` 落地時仍可點（anchor 有效），
   不要因為 head 不是字就判定 dead。
3. **重文可當第二個可點 key**：518 條「重文→正篆」是現成的庫內互鏈，不必等外部引用端；
   若要進 manifest，建議 kind 仍用 `char`（同一字條），別發明新 kind。

## 6. 過程更正（誠實記錄）

第一版掃描我犯了兩個錯，數字曾因此不可信，已全部重算：

- `plane(head.charAt(0))` 用 **code unit** 取首字 → 星體字頭被歸成 `U+D840` 這類半個代理對，
  一度報出「Ext-B 236」；正確是 **1,948**（Ext-A 987、Ext-C 2）。
- 佔位符統計用 `"？●□".includes(c)` 逐 code unit 比對，一度報出 `？: 10000`；
  正確是 **？ 4,445 次、含佔位符的字條 2,120 條**。
- Ext-B 上界我寫成 0x2FFFF（實為 0x2A6DF），導致幾百個码點各自成類、報告刷爆 50 KB。
